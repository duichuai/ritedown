# Ritedown — 开源 Markdown 编辑器方案（评估与实施）

> 日期：2026-11-13 ｜ 状态：已评审，项目定名 **Ritedown**

---

## 1. 项目背景与目标

### 1.1 背景痛点

- Typora 从 1.0 版本（2021 年末）起转为收费（$14.99），免费旧版停留在老标准，**不支持近年新增的 Markdown 语法扩展**。
- 市面上长期缺少一个「开源、免费、持续维护、支持最新语法标准、Typora 式写作体验」三/四者兼备的编辑器。

### 1.2 项目目标

开发一个支持最新 Markdown 标准的阅读与编辑器，采用**单一统一技术栈**同时覆盖浏览器与桌面端，开源到 GitHub。

### 1.3 已确认的关键决策

| 决策点 | 结论 |
|---|---|
| 产品形态 | **Web 编辑内核 + Tauri 2 桌面壳**，一套代码覆盖浏览器与桌面 |
| 编辑模式 | **双模式分期**：MVP 先做「源码 + 实时分栏预览」，二期迭代所见即所得混合渲染 |
| 前端框架 | 不设偏好，按编辑器内核生态兼容性选型（见 §5.3） |
| 项目定名 | **Ritedown**（rite = 书写 + down = markdown 尾缀；npm、GitHub 均无同名冲突） |

## 2. 先厘清：「最新 MD 标准」到底指什么

Markdown **没有单一官方标准**，「最新」实际由三层构成。方案必须明确声明支持哪几层，这也是开源项目对外宣传的核心卖点。

### 2.1 基础规范（必做）

- **CommonMark 0.31.2**（2024 年发布）：目前事实上的权威规范，所有「最新语法」的地基。

### 2.2 GFM 扩展（必做）

GitHub Flavored Markdown，写作场景中最常用的扩展集：

| 扩展 | 说明 |
|---|---|
| Tables | 表格 |
| Task lists | `- [ ]` 任务列表 |
| Strikethrough | `~~删除线~~` |
| Autolinks | 自动链接 |
| Footnotes | 脚注（GFM 已支持） |
| Alerts | `> [!NOTE]` / `[!TIP]` / `[!IMPORTANT]` / `[!WARNING]` / `[!CAUTION]` 提示块（2023 年新增，Typora 旧版不支持） |
| Disallowed raw HTML | 原始 HTML 白名单过滤 |

### 2.3 生态扩展（高价值，按期做）

| 扩展 | 说明 |
|---|---|
| Math | `$...$` / `$$...$$`，KaTeX 渲染 |
| Mermaid | 流程图、时序图、甘特图 |
| 代码高亮 | Shiki（VSCode 同款引擎，准确度最高） |
| Emoji 短代码 | `:smile:` |
| Front matter | YAML/TOML 元数据块 |
| MDX | 可选，暂不进路线图（复杂度高、场景偏开发） |

**结论：目标规范 = CommonMark 0.31.2 + GFM 全集 + Math + Mermaid + Shiki 高亮 + Front matter。** 每项扩展做成独立插件，可开关。

## 3. 竞品评估与机会点

| 产品 | 形态 | 所见即所得 | 开源 | 最新语法支持 | 维护状态 |
|---|---|---|---|---|---|
| Typora | 桌面 | ✅ 原生体验 | ❌ 收费闭源 | Alerts 等新特性滞后 | 商业维护 |
| Obsidian | 桌面 | ✅（CodeMirror 6 混合渲染） | ❌ 闭源（内核 API 开放） | 较全 | 活跃 |
| MarkText | 桌面 | ✅ | ✅ MIT | 一般 | **基本停滞**（多年无实质更新） |
| VSCode | 桌面 | ❌ 分栏预览 | 内核开源 | 插件补齐 | 活跃 |
| Zettlr / ghostwriter | 桌面 | ❌ | ✅ | 中等 | 活跃 |

**机会点**：MarkText 停滞留下了「开源 + Typora 式体验」的空位；同时没有任何主流编辑器把 **GFM Alerts** 这类 2023+ 新特性作为一等公民支持。本项目定位：

> **开源免费、支持最新语法标准、双模式（分栏预览 → 所见即所得）、Web 与桌面同构。**

## 4. 总体架构

```
┌─────────────────────────────────────────────────┐
│  宿主层（两个外壳，同一内核）                        │
│  ┌──────────────────┐  ┌──────────────────────┐ │
│  │ 桌面壳 Tauri 2    │  │ Web 部署（静态站点）    │ │
│  │ Rust: 文件IO/窗口  │  │ File System Access   │ │
│  └────────┬─────────┘  └──────────┬───────────┘ │
│           └──────────┬────────────┘             │
│                      ▼                          │
│  ┌─────────────────────────────────────────┐    │
│  │  应用层 apps/editor（Vue 3 + Vite）        │    │
│  │  界面：文件树 / 标签页 / 大纲 / 双栏 / 主题   │    │
│  └──────────────────┬──────────────────────┘    │
│                     ▼                           │
│  ┌─────────────────────────────────────────┐    │
│  │  内核层 packages/core（框架无关，纯 TS）    │    │
│  │  • 解析引擎：unified + micromark           │    │
│  │  • 编辑内核：CodeMirror 6                  │    │
│  │  • 渲染管线：mdast → hast → HTML/组件      │    │
│  │  • 语法插件：GFM / Math / Mermaid / ...   │    │
│  └─────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘
```

设计要点：

- **内核层框架无关**：核心逻辑（解析、渲染、编辑状态）不依赖 Vue/React，未来任何人可以把内核嵌入自己的博客、文档站。
- **文件读写抽象层**：桌面壳走 Tauri fs API，Web 端走 File System Access API（Chrome/Edge 支持），内核只面向统一接口 —— 单一方案覆盖两端，不维护两套兼容层。
- **语法扩展全部插件化**：`@ritedown/gfm`、`@ritedown/math`、`@ritedown/mermaid`… 内核默认零扩展。

## 5. 关键技术选型

### 5.1 解析引擎：unified / remark + micromark ✅

| 候选 | CommonMark 合规 | GFM Alerts | 扩展生态 | 结论 |
|---|---|---|---|---|
| **unified (remark + micromark)** | ✅ 官方合规实现 | ⚠️ remark-gfm 尚未支持，需自研扩展（已实现 `@ritedown/gfm-alerts`） | 最全（math/mdx/frontmatter 均有官方插件） | **选用** |
| markdown-it | 合规 | ❌ 需自己写插件 | 较全 | 备选 |
| marked | 部分 | ❌ | 一般 | 弃 |
| 自研 | — | — | — | 弃（合规性是核心卖点，不自造轮子） |

remark-gfm 内置 Tables/TaskList/Strikethrough/Autolink/Footnote；**Alerts 尚未被 remark-gfm 支持**，已作为第一个官方扩展 `@ritedown/gfm-alerts`（packages/transformer）实现并测试通过。Math 用 remark-math + KaTeX，Mermaid 走 hast 自定义节点渲染。

### 5.2 编辑内核：CodeMirror 6 ✅

| 候选 | 优势 | 风险 | 结论 |
|---|---|---|---|
| **CodeMirror 6** | 性能最强（百万行级）；markdown 语法树完整；decorations 可实现语法符号隐藏（Obsidian 同款路线，所见即所得的成熟先例）；框架无关 | 混合渲染需自研装饰逻辑 | **选用** |
| Milkdown（ProseMirror） | 所见即所得开箱即用 | 复杂表格/嵌套列表易碎，markdown 序列化保真度不可控，「语法损坏」是致命伤 | 弃 |
| TipTap（ProseMirror） | 组件生态好 | 同上，markdown 往返（parse→edit→serialize）易丢语法 | 弃 |
| Lexical | Meta 出品，轻快 | markdown 双向转换成熟度不足 | 弃 |

**选择理由**：源码模式天然完美（就是纯文本）；所见即所得模式走 CM6 decorations 实现「打字时显示语法、光标移开自动隐藏符号」，渲染永远由 remark 管线完成，编辑的是真实 markdown 源码 —— **从架构上杜绝 ProseMirror 系方案「编辑后语法损坏」的根因**。

### 5.3 UI 框架：Vue 3 + Vite + TypeScript ✅

- CodeMirror 6 与框架无耦合，Vue/React 均可；Vue 3 模板更轻、Tauri 官方模板支持好。
- 内核层不使用任何框架 API，Vue 只做宿主 UI。

### 5.4 桌面壳：Tauri 2 ✅

- 产物体积约 10 MB 级（Electron 约 100 MB+），内存占用低，Rust 后端天然提供文件 IO、窗口管理、系统对话框。
- Tauri 2 已支持移动端（iOS/Android），未来复用同一 Web 内核出移动壳，符合「单一方案覆盖所有终端」。

## 6. 功能规划（分期路线图）

### M1 — MVP：分栏编辑器（目标：可用、可开源发布）

- 源码编辑（CodeMirror 6，含语法高亮、行号、搜索替换）
- 实时分栏预览（remark 管线 + 滚动同步）
- CommonMark 0.31.2 + GFM 全集（含 Alerts）渲染
- 单文件打开/保存/另存为；拖拽打开
- 文档大纲（标题导航，点击跳转）
- 亮/暗主题；中文/英文界面
- Word 数统计；相对路径图片预览

### M2 — 体验增强

- Math（KaTeX）、Mermaid、Shiki 代码高亮、Emoji、Front matter
- 导出：HTML（自包含单文件）、PDF（桌面端）
- 所见即所得混合渲染一期：标题/加粗/斜体等行内语法符号自动隐藏
- 图片：粘贴/拖入自动复制到文档同目录并插入引用

### M3 — 工作区与文档库

- 文件夹工作区（文件树 + 多标签页）
- 工作区全局搜索（内容级，Rust 端 ripgrep 式搜索）
- 所见即所得二期：表格、代码块、列表等块级元素的混合渲染
- 导出 docx（调用 pandoc，桌面端可选依赖）

### M4 — 生态

- 插件机制（基于内核层插件协议）
- 移动端适配（Web 响应式）/ Tauri 移动壳
- 主题市场、语法插件注册表

## 7. 开源策略

- **License**：MIT（内核与全部官方插件）。
- **仓库结构**：pnpm monorepo（GitHub：`duichuai/ritedown`，官网：[duichuai.com](https://duichuai.com)）
  ```
  packages/core        # 内核：解析 + 渲染 + CM6 编辑内核（npm 发布 @ritedown/core）
  packages/transformer # 语法插件集：gfm/math/mermaid/...
  apps/editor          # Web 应用
  apps/desktop         # Tauri 2 壳
  docs/                # 使用与开发文档（中英双语）
  ```
- **工程化**：GitHub Actions（lint + 单测 + 跨平台构建产物）、vitest 单测（解析/序列化往返一致性测试是重点）、Changesets 版本管理、Conventional Commits。
- **冷启动**：先发 M1 到 GitHub + Reddit/HN/V2EX/少数派宣发，以「Ritedown：免费开源替代 Typora、支持 GFM Alerts 等新语法」作为差异化标签；官网与文档站使用自有域名 duichuai.com。

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 所见即所得混合渲染复杂度极高（Typora 闭源多年、MarkText 停滞即因难度） | **高** | 分期策略：M1/M2 先交付分栏模式保证项目活着；混合渲染拆成行内→块级两步走，渲染始终由 remark 管线统一负责，编辑器只做装饰 |
| 内核与宿主边界失守，后期无法独立复用 | 中 | monorepo 强制分层，内核层 CI 禁止 import 宿主层；发布独立 npm 包倒逼边界 |
| Web 端 File System Access API 兼容性（Firefox/Safari 不支持） | 中 | 桌面端为主战场；Web 端降级为「打开单文件 + 下载保存」，不做 polyfill 兼容层 |
| Mermaid/KaTeX 渲染性能（长文档多图） | 低 | 渲染结果按节点缓存，仅可见区域懒渲染 |
| 开源项目维护精力 | 中 | 架构上控制核心面（内核小、扩展多），M1 范围严格收敛 |

## 10. 结论

方案可行性高：解析、渲染、编辑三大核心均有成熟且合规的开源基座（micromark / remark / CodeMirror 6），无自造轮子风险；最大不确定性集中在所见即所得混合渲染，已通过「分期 + 渲染管线统一」策略降级。建议按 M1 → M4 推进，先以最小可用版本开源冷启动。
